# Components, theme and links

## Components

Every component is a `LitElement` with its own shadow root, carrying its own styles — there is no page-level selector reaching in, so each element is a markup change and nothing else to adopt in a new route. `src/components/theme.ts` exports two shared `css` chunks, `base` (box-sizing, font and colour inheritance onto `:host`) and `controls` (the button/input/select/label look), and every component composes them into its own `static styles` array alongside whatever is particular to it. Lit shares one `CSSStyleSheet` per `css` value across every component that adopts it, so importing `base` nine times costs one sheet, not nine.

Colour is read only through `--cr-*` custom properties — never a literal value — because those are what inherit through a shadow boundary. `src/routes/tokens.css` is the only place any of them is defined; a component reads one with `var(--cr-accent)` and defines none of its own. Dark is the default there and light is the variant, so a component that hardcodes a colour rather than reading a token also hardcodes a theme.

Touch sizing follows the same shape as colour: `--cr-tap` is the hit area a control grows to where the pointer is coarse, defined once in `tokens.css` and read through the cascade. Both `controls` and `src/routes/base.css` carry their own `@media (pointer: coarse)` block raising `button`, `input` and `select` to it, because a page-level rule does not cross a shadow boundary any more than a page-level reset does. The query is on the pointer, never on the width — a narrow window on a desktop is still a mouse. One control is deliberately smaller and says so with a more specific selector, which outbids the bare ones: a code run in `<code-bar>` (a full code wraps onto two lines, and two 44px rows inside a panel already pinned to an edge of the screen — the top on a wide one, the bottom on a phone — costs more than the target buys). Anything that is not a `button`, `input` or `select` — a nav link, a `<summary>` — gets its own rule, since the shared chunks never reach it.

`<code-bar>`'s tooltip bubble is behind `@media (hover: hover)` and is the one affordance with a touch counterpart rather than a touch equivalent: the bubble is drawn wide and centred on its run, so on a phone one over a run near either edge hangs off the screen and scrolls the page sideways. Tapping a run writes that run's hint into the message line under the code instead, through the same `status` channel a blocked clipboard uses, so a page's own `message` still outranks it and a decode error is never displaced by a label. (The combi page sets no `message` any more — its messages go to `<notice-bar>` — so on that page the line carries only the tap hints and, were Copy on, a blocked clipboard.) A copy that worked says so on the copy button rather than in that line: the line is empty most of the time, and one held open for a two-second sentence costs the panel its height for good. The write is unconditional rather than behind a `matchMedia` check, because a second definition of "is this a touch" in JavaScript is one more thing to keep in step with the CSS.

`base.css` opens by importing `@kcstyles/reset.css`, which is opinionated in one way worth knowing before debugging a layout: it makes every bare `div` a flex **column**. A page div that wants a row has to write `flex-direction: row` even after declaring `display: flex`, or it silently stacks — which is not a redundancy a reviewer should delete. A `display: grid` div is unaffected, since grid replaces the flex box entirely, and so is any element that is not a `div`.

`src/routes/base.css`'s body is three rows at every width, `auto auto 1fr`: the top bar (`<site-nav>`), the masthead, then `main`. There is no rail any more and so no breakpoint to move one — `<site-nav>` is a top bar at every width, and only its own styles compact it under 48rem. The `1fr` has to stay on `main`: put it on the masthead instead and a short page stretches that row to fill the screen, opening a gap of nothing above the content. And because `main` fills that row, a page whose `main` is a grid of several sections must pack them with `align-content: start` — the combi page does — or a short tab shares the leftover height out as gaps between its sections that change size with every switch of tab. `.container` (the masthead and `main`) is one centred column, `width: 100%` and `max-width: 68rem` with auto inline margins; the top bar and the footer are bands across the window. On the combi page every section inside that column — the sticky code panel included — spans exactly its width, so they share two edges; only the phone dock reaches out over the side padding, as a band across the bottom of the screen.

Reactive properties are declared with `@property()` and `@state()` from `lit/decorators.js` as plain class fields, not the `accessor` keyword the Lit docs lead with — `accessor` does not survive Bun's transpiler while `tsconfig.json` has `experimentalDecorators: true` set, which it does, with a FIXME linking bun#43097. `noImplicitOverride` is also on, so `static styles`, `render`, and every lifecycle method a component overrides (`connectedCallback`, `willUpdate`) need the `override` keyword, and so does a reactive property whose name collides with a member the DOM already declares — a `prefix` would, for instance, because `Element` has a readonly `prefix` of its own (its XML namespace prefix).

Every control dispatches its own untargeted `input` from the host, and the page listens for `input` on the enclosing form. The chips and cards are `<button>`s, so nothing composed escapes on its own and the host's event is the only one there is. Where a native control is involved the rule bites harder: a native `input` event is `bubbles: true, composed: true` and escapes the shadow root unaided, while `change` is not composed and dies at the boundary — so a component wrapping one has to stop the native event and re-dispatch its own, or the page hears a stale, composed echo of the control's last state. `<entry-tiles>`, `<entry-grid>` and `<code-bar>` additionally stop the `input` of the `<input>` inside their own shadow root outright: filtering a list is not a change of the control's value, and a code being typed is reported as a `code-draft`, not as a form change. `<theme-toggle>` follows the rule too, though nothing listens for what it dispatches: the top bar it renders inside sits outside the combi page's form. The rule has no exceptions, because "harmless where it happens to sit today" is not a property a component keeps.

Attributes carry markup-authored configuration; properties carry structured data the route hands over. Every `customElements.define` is guarded by `customElements.get`, because one `bun test` process shares one registry across every test file. Each component's file also augments `HTMLElementTagNameMap` with its own tag in a `declare global` block, so `document.createElement` and `querySelector` return the class type — there is no central declaration file to edit.

`<site-nav>` and `<tool-index>` read the registry themselves; no route passes them data. `<site-nav>` renders `<theme-toggle>` as one of its own children, so there is no mount order for a page to get wrong.

`<site-footer>` is the third of those: it calls `readBuildInfo` from `#lib/build-info` in `render` rather than being handed a commit and a date. At render rather than at module load, so a test that sets the environment gets a component that sees it — which is the only way to exercise the populated line, since the values are absent under the test runner exactly as they are in development. Every field it shows is nullable and each drops its own segment; a page that knows neither says `local build`, which is what every `bun run dev` and every local `bun run build` shows. `src/lib/tools.test.ts` asserts every page hosts the element, beside the same assertion for the top bar.

`<code-bar>` lays the code out as a column: the code takes a line of its own and every button sits on the one below, because a full code beside four buttons either wraps at an arbitrary character or squeezes the code down to fit them. The button row carries a default slot after Copy, so a page that has its own buttons for the code it is showing — the combi page's Save and a `<details class="more">` ⋯ menu holding Copy code, Copy link, Reset, Save as new and Cancel — puts them in that row rather than in a row of its own. `copyable` (default `true`, a property the route sets) hides the bar's own Copy for a page that offers Copy code elsewhere; the combi page turns it off, so its panel shows exactly Edit, Save and ⋯. Copy stays in the component for any page that wants it. The editor renders no slot: a code being typed is not the code those buttons act on, so they leave the panel with the display and come back with it. A slotted button is light DOM, styled by the page, and `::slotted(button)` in the bar matches it to Edit and Copy. The code wraps onto as many lines as it needs, at every width; on a coarse pointer every run, inert or not, takes the same taller box and an explicit line height, so the dotted underlines along a wrapped line sit at one height. The underline is text decoration, not a bottom border: WebKit boxes a button and a span differently, and on iOS a border stepped up and down along the line. The combi route lets each section of its `main` be narrower than its content (`main > * { min-width: 0 }`), so no unwrapped line can widen the page.

`<code-bar>` is both halves of the combi page: it shows the code and it is the only place a code is entered. It decodes nothing. Typing reports a `code-draft` with the text so far; the page decodes that and hands back a `value`, and may hand back a `message` and an `invalid` flag for the line under the code — that is the element's generic contract. The combi page uses only `value`: its messages, the decode error included, go to `<notice-bar>`. Clicking a run of the code emits `slot-jump` with that run's group name, which the page turns into the control to focus. Escape closes the editor and emits `code-cancel`, which is the page's cue to put the built code back. Every way the editor closes — Enter, Done, a blur, Escape, the page setting `editing` false — also emits `code-close`, fired from `updated` when `editing` goes from true to false; the combi page uses it to let a held typing-progress notice clear itself.

`<notice-bar>` is the combi page's one place for a message. `show(type, text, options)` replaces whatever is showing with one of three types — `info`, `warn`, `error` — where `text` is a line or a list of lines and `options.title` heads a list (the decode warnings' "Read with changes"); `clear()` empties it, and the ✕ button (`aria-label="Dismiss"`) does the same. Info and warn are spoken through a `role="status"` region, an error through a `role="alert"` one; both regions are always rendered, so a screen reader is already listening when a message arrives. Each type's colour comes through a local `--tone` set from tokens only: `--cr-accent` for info, `--cr-blessed` for warn, `--cr-danger` for error, as the box's edge and a 12% wash, never as text colour (the amber fails 4.5:1 as text on paper). An info message clears itself after `infoFor` milliseconds (5000; a property so a test can shorten it) unless shown with `options.hold`, which keeps it up until `release()` — the typing-progress line, held while the editor is open. Warn and error stay until dismissed or replaced. Empty, the host has no `type` attribute and is visually hidden and absolutely positioned, so it takes no room and no grid track in `main` but stays in the accessibility tree; a live region that is `display: none` until it speaks is often not heard. Moving the element (the route carries it into an open drawer) disconnects and reconnects it, so `connectedCallback` re-arms an info message's timer that `disconnectedCallback` dropped. The ✕ fires `notice-dismiss` (bubbling, `detail.focused` saying whether the ✕ had focus): the ✕ goes with the message, focus on it would fall to `<body>`, and only the page knows where it belongs instead.

The editor's text is held in the element's own `draft` state, seeded from `value` when the editor opens, and `value` is deliberately not written back into the field while it is open — the page decodes every keystroke and writes a new `value`, so binding the field to it would fight whoever is typing for the caret. `value` is the one observed attribute, because the markup ships an initial code and the page sets a new one on every change; setting it also puts the copy button back and clears the copy status, since a button still saying "Copied" beside a code that has since changed is a lie.

`<code-bar>`'s `hints` property takes one `{ char, hint, group }` per character of the current value and draws each run of one group as a `<button>`, with the tooltip bubble as its own CSS keyed off a `data-tooltip` attribute the component defines and styles itself. It labels; it never decides what a character means — that is the page's job. A list whose length does not match the value is dropped whole rather than misaligned, and setting `value` clears the hints, since against a newer code they would point at the wrong characters. A hint's optional `inert: true` — read from a run's first hint, the same way `group` is — draws that run as a plain `<span>` instead: no tab stop, no click, no `slot-jump`, though its tooltip still shows. The page sets it for a run nothing owns (the version character, a reserved slot) or whose tab the episode has no room for, since a jump with nothing behind it is worse than no jump at all.

`<card-group>`'s `selected` getter reads an internal `Set` of ticked values rather than the rendered cards — Lit owns that DOM, so reading it back would be reading this element's own output rather than its state. The getter filters the element's own `options` against that set rather than reading DOM or click order, which is what keeps boosts and cookie powers in table order: part of the wire format, not a preference. `<entry-tiles>`'s getter follows the same rule for the same reason: a treasure slot's alternatives are written in id order, so click order would produce a different code for the same slot.

All four value-holding list elements — `<card-group>`, `<entry-tiles>`, `<entry-grid>` and, in its own way, `<chip-group>` — refuse a value their current `options` do not contain. `<card-group>` and `<entry-tiles>`, the two multi-value ones, do it in `willUpdate` as well as in the setter — the setter alone is not enough there: `options` and the selection are two separate writes, so a list replaced underneath a pick would leave the dropped value in the internal set, invisible while it has no card and back the moment a later list contains it again. `<entry-grid>` and `<chip-group>` each hold one value instead of a set, so a getter that checks it on the way out is enough on its own: `<chip-group>` falls back to its first option whenever the value names none of them — which is what the `<select>` it replaced read as, and what `render` marks checked, so the getter can never disagree with the screen — while `<entry-grid>` falls back to `null`, since a grid with nothing picked is already a state its own None cell or the episode's `any` can draw.

`<chip-group>` is a radio group wearing the site's button look: one tab stop for the whole row, arrows moving the choice as well as the focus, Home and End at the ends, clamped rather than wrapped. It replaces a `<select>` wherever the list is short enough to show whole — seeing the twelve episodes at once is the point, and a closed select hides eleven of them.

`<build-summary>` reads the whole build at a glance, with pictures, and each row is a way to the control behind it. It declares its own item vocabulary — `SummaryItem` is text (optionally muted), a pill (tone `semi`), an image (a null `src` draws the text alone, or the `title` when there is no text either, so no item is ever invisible; `badge` is the `+N` corner badge, `note` the small level text, `title` the hover text, `mark` — `evolved` or `blessed` — the treasure form drawn on the picture as the kind's letter in its top corner and a ring in `--cr-evolved` / `--cr-blessed`, with the kind's name added to the alt text, since an evolved treasure and the blessed one beside it share a picture; a base form carries none; `caption` the name drawn small under the picture, two lines at most, which also takes over from the alt text so the name is read once), a stack of at most two overlapping faces (its `text` when given; else its `caption` under the faces; otherwise its `title`, as the hover text and as visually hidden words for a screen reader, or on screen when there are no faces), a `·`/`→` separator, or a tag — and `SummaryRow` is `{ label, target, items }`, where `target` is opaque to the element. Each row is a `<div class="row" data-target>` ending in a `<button class="open">` labelled "Open <label>"; that button fires `summary-jump` (bubbling, `detail` the target) and nothing else. A row of pictures with captions makes its value a `<button class="names" aria-pressed>` instead: pictures lead, every one in the same 2.75rem box so a row reads as a grid, and a click there shows or hides that row's names, and only that row's — the private `named` set of targets, drawn as a `data-names` attribute on the row, which widens that row's boxes alike. The › keeps the row's right edge at every width; on a phone the label stands over the pictures beside it. With names hidden a picture's alt text (or a stack's visually hidden words) is its caption, so a screen reader still hears the name. None of these fires anything the page hears as a change — never `input`, `change` or `toggle`, since the page re-renders the build on `input` and the summary is a picture of the build, not a control in it (it sits outside `#build` as well). `hint` is the muted line under the rows, `null` for none. On a phone (`width < 48rem`) the rows are hidden behind one `<button class="line">` of the `compact` items plus ▾ — always one line: what does not fit fades out at its end while the ▾ stays, which is why the route puts the boost count before the pictures and leaves the treasures' level notes out of it; tapping it sets the private `expanded` state, reflected by hand onto the host as the `expanded` attribute the stylesheet reads, and a "Hide ▴" button above the rows clears it. Focus moves to whichever of the two takes the pressed one's place. The fold is never remembered and never announced. The combi route builds all three properties from the decoded build with `summaryOf` in `src/routes/combi-name/summary.ts`, and maps `summary-jump` to the same `jumpTo` a code letter's `slot-jump` uses; the route's targets are the `hints.ts` group names. The auto verdict is no longer this element's: the route writes it as a sentence into `#verdict` under the mode chips.

`<tab-strip>` draws only the row of tabs, one tab stop for the row, and fires `tab-change`; the route owns the light-DOM `role="tabpanel"` sections and shows the one matching `value`. Each panel is named by its own `aria-label` rather than by `aria-labelledby` pointing at its tab, because the tabs live in the strip's shadow root and an id reference cannot cross a shadow boundary, so the label would resolve to nothing. The panel ids are a table in the route (`PANEL_IDS`), not `panel-${tab}`: content blockers hide consent banners with generic cosmetic rules, and EasyList Cookie, Fanboy's lists and AdGuard's cookie-notice list all carry `###panel-cookies`, so under uBlock Origin, AdGuard or Brave the Cookies tab painted as nothing at all while every headless check passed. The Cookies panel is `#panel-roles`, and a route test holds every light-DOM region's id clear of "cookie". Name a light-DOM region or container (a section, panel, dialog, form, header, aside or main — what the test checks) after what it does, never "cookie"/"consent"/"gdpr" — a page about Cookie Run is the one place that word is tempting. Three control ids still carry the word: `#cookie` (an `<entry-grid>`), `#cookiePowers` and `#field-cookiePowers`. They are known, no generic rule in EasyList Cookie, Fanboy's lists, uBlock's cookie annoyances or AdGuard's cookie list matches them today, and renaming them reaches into the tests and the jump wiring, so they stay for now; a list adding `###cookie` or an id-prefix rule would hide them.

`<card-group>`'s `legendHidden` takes the legend off the screen without taking it out of the tree — `position: absolute` and `clip-path: inset(50%)`, the same trick `<theme-toggle>` uses on its own label — for a group the page has already given a heading of its own. The fieldset keeps its name, because an unnamed group of seven checkboxes is a worse answer than a name said twice, and `display: none` would take the name away with the text. It is a property the route sets rather than an attribute the markup ships, for the same reason `resettable` is.

`<card-group>`'s third option field is a *list* of pictures, not one: a cookie power+ can belong to several cookies or pets at once — Serenade of Love to two, EXP Party to four — and the card lays them out from a `data-count` attribute on its own frame. An empty list is what falls back to the lettered tile, so "no art" and "one picture" are the same code path with a different length. A boost passes a list of one, which is the same path again.

`<chip-group>`'s third option field is optional and holds one picture or `null` — a thumbnail drawn before the label. No row passes one today: the episode row did, and it is an `<entry-grid>` now, which is what a list of twelve landscape cards wanted to be. The rows left are words — a mode or a goal is not a place — so a chip given nothing is the bare chip every row was before pictures arrived. The field stays because the sizing answer it carries is not obvious and is easy to get wrong twice: the thumbnail is sized by height with its width left to follow, rather than boxed into a square, since an episode card is landscape, 320 by 210, and a square frame letterboxes it down to a stamp. Height is the length that has to stay equal across the row, because it is what sets how tall the chips are.

`<entry-tiles>` is the one catalog control left behind a dialog: it renders a tile button on its host, naming the current pick, and opens a `<dialog>` with `showModal()` rather than an inline grid, because the treasure catalog runs from 94 to 1,144 entries and three slots of that is a wall of scrolling even filtered. Only the first 50 matches are rendered in the grid, and a picked treasure the filter hides is still held and still listed under the slot, but it leaves the grid. Its cells are a roving tabindex — one tab stop per dialog, arrows and Home/End inside it, clamped at the ends. The arrow walk is linear in every direction on purpose: how many cells sit on a row is a layout answer the element would have to measure, and a walk that guesses wrong is worse than one that is consistent. The platform supplies the dialog's backdrop, its focus trap, and Escape, so the component does not have to close it from the outside on its own — but a native dialog does not light-dismiss, so it still carries a `click` handler on its own `<dialog>` that closes it when the click lands on the backdrop rather than inside `.sheet`. A click fires on the nearest common ancestor of the press and the release, though, so selecting text in the search box and releasing past the sheet's edge would target the dialog the same way a real backdrop click does; the component latches on `pointerdown` which element the press itself targeted, and only closes on `click` when the press agrees, so a drag out of the sheet cannot pass for a deliberate dismiss. Escape, the header's Close button, and a backdrop click all return focus to the tile. A pick itself does not close the dialog, unlike a single-value picker: several picks in a slot are alternatives, not one value replacing another, and closing the list is covered in its own right below. The backdrop itself reads `--cr-backdrop`, the one token added for it, rather than a literal — the same rule every other colour on the site follows. A modal traps focus but not scroll, so the component calls `lockPageScroll`, exported from `src/components/tile.ts` beside `tileStyles`, when it opens its dialog — the same function the route's own Saved and Help drawers call to hold the page still behind them. The function sets `overflow: hidden` on the document element and also pins `<body>` with `position: fixed` at minus the current scroll offset. `overflow: hidden` alone is not enough: iOS ignores it and scrolls the page once the keyboard is up for the search box. The function returns an unlock that restores both and scrolls back to the saved offset. The component calls it from the dialog's `close` handler, which every way of closing passes through, and from `disconnectedCallback` if the dialog was still open. `.entries` also carries `overscroll-behavior: contain`, so a swipe that reaches the end of the grid stops there rather than passing on to the page. The dialog's height cap is `85svh` where supported rather than `85vh`: on a phone `vh` is the viewport with the toolbars hidden, so a dialog sized to it runs behind the toolbars that are showing when it opens.

`<entry-grid>` draws the same catalog look inline instead, for the four lists short enough to put on their tab whole: episode, cookie, relay and pet. `required` drops the implicit None cell, for a list that already carries its own none — the episode's is `any`, one of `ALL_EPISODES`' own options, so a second None cell above it would be a second answer to the same question; cookie, relay and pet leave `required` at its default and get the grid's own None cell instead, since the build can simply never mention them (`anyIdFor`'s `__` sits in the catalog itself, as their "any"). With no None cell nothing holds the empty value, so the grid's tab stop falls to the first cell until something is picked — the one state `required` exists for, and why the episode grid always opens on an entry rather than nothing. `searchable` draws the filter box, off by default: twelve episodes are a grid worth seeing whole, not a catalog worth filtering, while cookie, relay and pet turn it on for their own catalogs. Both are properties rather than attributes, for the same reason `resettable` and `legendHidden` are — an attribute the markup ships is invisible to the property in the route's test harness. There is no 50-cell cap here, unlike `<entry-tiles>`'s dialog: the Cookies tab shows only the picked role's grid at a time, the other two `hidden`, so one open catalog's full length is what the tab ever costs, not several at once. An inline grid never scrolls inside its own box: every cell shows at full height and the grid grows the page. `tileStyles`' `.entries` carries the dialog's scroll rules (overflow, flex, min-height, overscroll-behavior), and a later rule only undoes a property it names, so `<entry-grid>` restates each of them — overflow as two longhands, since happy-dom does not let the shorthand override an earlier sheet's `overflow-y` and the test guarding this would read `auto`. Left on `auto`, a one-pixel rounding in WebKit at 110% zoom made the episode grid a box that scrolled by itself.

`<chip-group>`'s `labelHidden` and `<card-group>`'s `legendHidden` do the same job for the same reason: the page gives every field a heading of its own, so a control's own copy of that name comes off the screen while the radiogroup or fieldset keeps it. `<chip-group>` can hide the span outright because its radiogroup reads its name from `aria-label` rather than from the span; `<card-group>`'s legend is the fieldset's name, so that one is clipped rather than removed.

`<entry-tiles>` is not one button: the slot's name opens the picker, and beside it each alternative is a row of its own, with a dashed "or" between two of them (an `aria-hidden` `<li>`, so a test counting picks selects `li.chip`). The combi page stacks its three slots as full-width rows rather than columns, because side by side they were half-names. The host is an inline-size container, and the layout follows the slot's own width rather than the window's: from 36rem the slot's name is a column on the left, and below that it is a bar above the picks. Each row shows the art, the full name with its kind, a summary of its levels (`+9`, `+7–9`, `+0, +2–4`, `any`; `aria-hidden`, since the buttons already carry the state), and the remove button. Under them, or in line once a fine pointer has 42rem of row, sits a strip of ten buttons, +0 to +9, labelled "<name> levels" with `aria-pressed`. One strip rather than a 5×2 grid, so the levels a pick holds read as a lit range at a glance. A press toggles one level, never releasing the last one, since a treasure has to accept at least one level. It is a toggle rather than "hold this level alone" because a touch screen has no modifier key, and +2, +4, +6 has to be reachable there as well. Holding a level for `LONG_PRESS` (exported, 500ms) holds it alone, so +0 to +9 is still one gesture. A press that drags across the strip holds the range it covers, and shift-press holds the range from the anchor (the last plain press on that pick, else its lowest held level). A hold or a drag has already answered the press, so the click that ends it is swallowed rather than toggling the cell it lands on. The flag is cleared one task after the release, because a release off the strip produces no click and the next real one must not be eaten. Pointerdown releases any implicit touch capture, so pointerover keeps landing on the cell under the finger. The buttons are `touch-action: pan-y` so a vertical swipe still scrolls the page, and the strip cancels `contextmenu` and the touch callout so a held finger is not taken for a menu request. Beside the strip, an `any` button (`aria-pressed`) holds all ten levels, or goes back to +0 when all ten are already held. A wide-strip rule inside the container query has to outrank the bare `.levels` rule that follows it, which is why it is written `.chip .levels`: at equal specificity the later rule wins and the cells shrink to fit. Under the last alternative, a dashed "+ Add alternative" button opens the same picker as the slot's name, because a filled slot's name reads as a label. An empty slot drops the name column, so the whole frame is the button. No press dispatches `input` unless the levels actually changed. A level belongs to the pick, not the slot, and leaves when the pick does — a treasure dropped and picked again starts over at +0 rather than coming back at the level it left with. The `levels` property reads and writes alongside `selected` on the same terms: the getter returns an entry for every selected value, its levels ascending, defaulting to `[0]` for one nobody has touched, while the setter drops any entry whose value is not currently selected — which is why a caller writes `levels` after `selected` rather than before it. The remove button lives on the row rather than inside the opening button, because a button inside a button is not markup, and it commits straight away rather than through a draft: there is nothing there to cancel, and a list you have to confirm a deletion in is a list you cannot tidy at a glance. Focus lands on whichever remove button takes the gone one's place, or on the slot's own button once the list has emptied.


`<entry-tiles>`'s fourth option field is the entry's kind — `base`, `evolved` or `blessed`, or absent — and it is the only thing telling two of its cells apart where the catalog cannot: an evolved treasure and the blessed form beside it share one picture, and 267 of the 1,144 entries are half of such a pair, while their names differ only by a prefix. The component knows the three slugs and nothing else about treasures; `kindFor` in `src/routes/combi-name/catalog.ts` turns the index's own `N`/`E`/`B` into them, so the alphabet stops at the route. An option carrying no kind, or one the component's table does not know, is drawn exactly as every option was before kinds existed — no badge, no ring, no claim — which is what keeps the cookie and pet lists honest.

A kind is drawn three ways at once, because colour alone is not a distinction anyone can rely on: a lettered badge on the corner of the art, a ring in the kind's colour — on the art rather than on the cell, since the cell's own border already carries the picked state — and the kind's name appended to the cell's `aria-label`. On the closed line the chip wears it as its border and a bar down its start, which is the question a built slot has to answer at a glance. The colours are `--cr-evolved` and `--cr-blessed` in `tokens.css`; a base form borrows `--cr-muted`, since tinting the common case tints most of a 936-entry grid. The component routes whichever is in play through a local `--kind`, which is plumbing rather than a site token — every value it takes is defined in `tokens.css` and read from there.

The kind filter row above the search box narrows the grid to one kind, and doubles as the colour key for the badges, each button wearing the swatch it filters to. It appears only when the options actually carry kinds. Like the search box it narrows what is shown and nothing else: a pick it hides is still held and still on the closed line, and moving it dispatches no `input`, because narrowing a list is not a change of what the slot holds.

An image inside one of these frames carries the frame's measurements itself rather than a percentage of them. The frame is a grid area, so a percentage height — `height` and `max-height` alike — has nothing definite to resolve against, and the portrait falls back to its own height and overflows onto the name below it. Where a frame's size changes, the image's must change with it. The picker grid's rows are `grid-auto-rows: max-content` for a related reason: WebKit sizes an auto row of buttons in a flex-shrunken grid to the buttons' min-height, which under a coarse pointer is `--cr-tap`, so on iOS every name spilled into the row below it. Chromium does not show this, so check the picker in WebKit after touching `.entries`.

Each component is standalone in its logic, apart from the shared style chunks: every one imports `base` (most also `controls`) from `src/components/theme.ts`. `tileStyles` is the one style chunk that lives beside its own file rather than in `theme.ts` — it is exported, along with `glyphFor` (the initials an entry falls back to when the catalog has no picture) and `lockPageScroll`, from `src/components/tile.ts`, a file with no component of its own, imported by `entry-tiles.ts` and `entry-grid.ts` for the look the two catalog controls share. Presentation is shared; the logic and the `Option` types are deliberately not — `<chip-group>` and `<card-group>` each declare their own `Option` type rather than sharing one, and `<entry-grid>` and `<entry-tiles>` do the same. A shared type between two components is the first step towards a component that cannot be read on its own. Beyond the style chunks, only `site-nav.ts`, `tool-index.ts` and `site-footer.ts` import anything else — `TOOLS` and `hrefFor` from `src/lib/`, `build-info` in the footer's case, plus `theme-toggle.ts` in the top bar's, since it renders one.

A CSS comment inside a `css` tagged template must not contain a backtick: it closes the template literal, and the failure surfaces as a parse error in the bundler rather than from the typechecker or Biome. Name a property in prose — max-height, not the quoted form.

`src/components/` imports from `src/lib/` and never from `src/routes/` — `src/components/build-summary.ts` declares its own `SummaryItem` and `SummaryRow` rather than importing anything from `src/routes/combi-name/`, and `<code-bar>` declares its own `CharHint` rather than importing the one `hints.ts` exports. That is what keeps the arrow pointing one way.

Tests reach into a component through `shadowRoot` and await `updateComplete` after any change, since Lit's render is a microtask rather than synchronous. A handler that restores focus into a grid that just redrew — `<entry-tiles>`'s toggle, and `<chip-group>`'s arrow walk — awaits its own `updateComplete` before it does, so a test asserting where focus lands has to settle twice: once for its own await, which resumes after the handler's, and again to actually observe the result. A plain click needs no second settle: `<entry-grid>`'s pick calls nothing for focus at all, leaving it exactly where a mouse click already put it, and `<entry-tiles>`'s dialog `close` handler refocuses the tile synchronously, since the tile sits outside the grid being redrawn and is there to focus whether or not Lit has caught up. The component test files carry a `settle()` helper (`updateComplete` plus a zero-length `Bun.sleep`) for exactly this. A value bound with `.value=${...}` is a property and not an attribute, so a test looking for one control among several finds it by reading `button.value` back, not with an attribute selector.

What no test can show: happy-dom never resolves an inherited custom property, so nothing here proves a `--cr-*` token actually reaches a component, or that a colour, a border, or a layout looks right. The browser is the only verification that layer gets — a full green suite is not evidence the page is styled.

Nor does happy-dom replay an attribute that was already on an element when the element upgraded. The route test sets `document.body.innerHTML` before importing the page script, which is what defines the components, so every attribute in that markup is invisible to the property it configures — `label` reads back as `""` there, and a boolean like `resettable` as `false`, while both work in a browser. So a behaviour the markup turns on cannot be tested through that harness at all. `<chip-group>`'s `resettable` is a property rather than an attribute for that reason as much as for tidiness: the route that decides which option comes first is the honest place to say that clicking the chosen chip goes back to it.

## Theme

`src/components/theme-toggle.ts` owns the light/dark choice. `src/routes/tokens.css` paints dark by default, light under `prefers-color-scheme`, and obeys `data-theme` on the root over both, so the whole feature is: remember a choice and write that attribute. Three states, and "system" is the absence of one — it removes `data-theme` and deletes the stored key rather than writing a third value, which is what hands the page back to the OS.

Each page's `<head>` carries a small inline copy of the read-and-apply step, marked `id="theme-boot"`. The module scripts are deferred, so without it a page paints in the system theme and flips once the saved choice loads. `src/lib/tools.test.ts` asserts every page has it.

Every storage call is wrapped: a browser that refuses `localStorage` still themes the page for that visit. `readTheme`, `writeTheme`, and `applyTheme` are plain functions exported alongside `<theme-toggle>` rather than folded into its `connectedCallback`, and the storage-refused test calls them directly rather than going through the element — a custom element hands a `connectedCallback` exception to the global error handler instead of throwing to whoever appended it, so routing that test through `<theme-toggle>` would pass whether or not the wrapping actually worked.

## Link shape

`hrefFor` in `src/lib/href.ts` writes every cross-page link, and writes it twice over:

- Served over http(s) it emits directories — `./combi-name/`, `../` — so the address bar reads `/combi-name`, not a filename.
- Under `file:` it appends `index.html`, because opening `dist/` from disk means nothing is there to serve a directory index and the bare directory link would dead-end.

Both forms stay relative, and that outlives the reason it started. The site was served from a GitHub Pages project subpath, where a root-relative `/combi-name` would have resolved against the domain root and missed; it now serves from a Cloudflare Worker at its own root, where such a link would happen to work. Relative links are still what the `file:` build needs, and they cost nothing, so the rule stands — but do not restate the old subpath justification as if it were live. A test covers all four combinations of depth and protocol; that is the guard against someone "simplifying" it back to one form.

`hrefFor` is `src/lib/`'s one deliberate brush with the DOM: it defaults its `protocol` argument to `globalThis.location?.protocol`, because every caller would otherwise pass the same thing. That is a default rather than a read — `src/lib/href.test.ts` hands the protocol in on every call and never touches `location`.
