# The combi codec

The character tables at the top of `src/routes/combi-name/codec.ts` are the single source of truth, and everything else derives from them:

- `GOAL_SLOT`, `MODE_CHARS`, `EPISODE_CHARS`, `BOOST_SLOT`, `RANDOM_BOOST_CHARS`, `COOKIE_POWER_SLOTS`, `ACTION_CHARS` define both the encoding and the set of valid values. Every character is meant to be read: a letter from the name of what it holds, a digit where the value is a number, `0` for off. The three multi-select fields are `SetSlot`s: one slot holds any set of a few members, a lone member is its own letter, and each combination of two or more takes a running character from `combos` (digits first, so a digit reads as "more than one"). Goals are one such slot (`Combi.goals`, empty for Any), and so are boosts; cookie power+ is three, one per group of the seven powers.
- `ALL_GOALS`, `ALL_MODES`, `ALL_EPISODES`, `ALL_BOOSTS`, `ALL_RANDOM_BOOSTS`, `ALL_COOKIE_POWERS`, and `ALL_ACTIONS` are computed from those tables — never hand-maintain a parallel list.
- `EPISODE_LIMITS` / `limitsOf` say what an episode lets a run carry: Special Episodes 1 and 2 and the Special Exp Episode take no boosts, random boost, cookie power+ or relay; the Exp episode no treasures either; Special Episode 2 alone has a floor. `normalize` drops what an episode (or a manual run's action) has no room for; `encode` always writes through it, `decode` applies it and warns about what it dropped. The relay and treasures are the loadout's, so `fitLoadout` in `full-code.ts` drops those, with `loadoutWarnings` beside it.
- `src/routes/combi-name/labels.ts` maps every value to a display name. A test asserts key-for-key parity with the `ALL_*` arrays, so a new value cannot ship unlabeled. No error or warning the codec raises quotes a display name, so every name lives here, boosts included.
- `src/routes/combi-name/describe.ts` turns a `Combi` into display rows plus an auto/semi-auto verdict, and a `Loadout` into its own rows. It is the only place that decides how a combi or a loadout reads in prose. `hints.ts` reads `describeLoadout`'s rows, `index.ts` and `summary.ts` both read `describeBuild`'s verdict — the route for the Main tab's verdict sentence, the summary for its Run row's pill — and `entryName` — which appends a note to an entry the site has since dropped — stays private to the file: both `describeLoadout` and its own `treasureRow` helper call it, so that note reads the same wherever a loadout entry is named.
- `src/routes/combi-name/hints.ts` says what each character of a code means, one entry per character, for the tooltips on the built code. Slot numbers come from the codec's own tables and the values from `describe.ts`, so a table that grows cannot leave a stale hint behind. A code it cannot decode gets no hints at all rather than half a labelling, which would point at the wrong characters. Its `group` field carries a second job now: `<code-bar>` draws each run of one group as a single button and emits that group name when the run is clicked, and `index.ts`'s `OWNER` map turns the name into the control to focus. A group added here without an `OWNER` entry simply does not jump — it does not break. The treasure group is split for the code bar: `treasureOrder` for the `T` and its order flag, then `treasure1`-`treasure3`, one per slot with the `.` that closes it, each jumping to its own control; every one shares the group's whole description as its hint, and the summary's single `treasures` row still jumps to the first slot. Each hint also carries a `name`, the slot and field without the value, which is what a tap says under the code.
- `src/routes/combi-name/art.ts` says which cookies or pets each cookie power+ belongs to, so the cards can wear their faces. Each entry is a list of `{ section, key }` against the catalog's own keys rather than wire ids — five powers name one cookie, Serenade of Love the two pets that sing it, EXP Party the four cookies that throw it. A test asserts key-for-key parity with `ALL_COOKIE_POWERS`, the same guard `labels.ts` has, so a new power cannot ship without the page deciding what face it wears. The codec still does not model a cookie — this mapping is the page's, not the format's. `BOOST_ART` and `EPISODE_ART` beside it do the same job for the boost cards and the episode picker's cells, naming the authored key each one's icon is filed under in `assets/index.json` and resolving it through `catalog.ts`'s `staticImage`. Both carry the same parity test, and both have entries the other end lacks in one direction or the other: `any` is the episode with no icon, while the index holds one boost and two episodes the codec has no character for. To add a boost or episode, that is the third table to fill in after the character table and the label table — and the test fails until you do.
- `src/routes/combi-name/index.ts` pairs each `ALL_*` array with its label table and hands the result to the form components as their `options` property. `src/routes/combi-name/index.html` declares those elements empty on purpose — do not hardcode options into the markup.

To add an episode or cookie power: add it to its character table, its label table, and its art table in `art.ts` (and to `EPISODE_LIMITS` if it takes less than a full run). Nothing else needs touching, and tests fail until all three are done. A fifth boost is not that simple: every set of boosts has its own character in slot 5, so a fifth doubles the sets to 32, which crowds the alphabet. A new cookie power joins one of the three groups and needs combination characters for every set it makes with that group's members — keep groups small.

## Ordering is part of the wire format

`Object.keys` order determines the `ALL_*` order for the character tables, and the `members` order of `GOAL_SLOT`, `BOOST_SLOT` and `COOKIE_POWER_SLOTS` determines `ALL_GOALS`, `ALL_BOOSTS` and `ALL_COOKIE_POWERS`. A character is written out per value, never derived from position, so reordering a `*_CHARS` table moves the chips on the page without changing what a character means — except for a `SetSlot`, whose `combos` keys spell each set in `members` order, so reordering members breaks every combination key; and which group a power sits in decides which slot it is written to. Changing a character moves the wire format. If the slot layout or a character mapping has to change, bump `VERSION` in `src/routes/combi-name/codec.ts` — `decode` rejects any other version outright. (`VERSION` is still `1` after the move to goal + mode slots and lettered boosts and powers: the owner chose a breaking change over a bump. Goals becoming a set needed no bump at all: a lone goal kept its letter and Any its `0`, so only characters no code had used were added. A whole cookie power+ group moving from `4`/`1`/`1` to `A`, so all seven read `AAA` like all four boosts or goals, was a break with no bump either, by the owner's choice: an old code carrying one fails to decode rather than reading as something else.)

The layout: 1 version, 2 mode, 3 goal, 4 episode, 5 boost set, 6 random boost, 7-9 cookie power+ (one set slot per group: Cheerleader/Special Force/Fairy, Cheesecake/Sea Fairy, Serenade of Love/EXP Party), 10 action. On Special Episode 2 slots 5-7 are the floor instead, `000` for any and `001`-`100`, and slots 8-9 must be `00`; `decode` reads slots 5-9 by the episode in slot 4.

The form end of that guarantee is `<card-group>`'s `selected` getter, and `<chip-group multiple>`'s `values` getter for the goals: each filters the element's own `options` rather than reading click order, which is what keeps goals, boosts and cookie powers in table order.

## Semi-auto is derived, and the page says so by not offering it

`ALL_MODES` carries `semiauto` and `MODE_CHARS` maps it to `H`, because a code
carrying `H` has to decode — but the page's mode chips are `ALL_MODES` minus
that one. A manual run is `0` and is never touched by this rule. Goals are a
set: an auto run picks 1-3 of Money, Exp and Box (`AUTO_GOALS`) and a manual
one 1-4 of Score, Money, Exp and Box (`MANUAL_GOALS`); the last goal on cannot
be clicked off. Any (`0`, an empty set) is an auto run that specialises in
nothing — no longer offered, but a code that says it still decodes and shows
as a goal row with no chip on. Switching to auto drops Score and falls to Money
if nothing is left; a manual run left with nothing lands on Score. A code
saying Score beside `A` or `H`, alone or among others, or Any beside a manual
`0`, decodes with a warning. Semi-auto is what `normalizeMode` makes of an auto run when Fast
Start, a random boost, a jump action or a relay cookie is in play, so a chip for
it could only disagree with the code those produce. `writeForm` lands a decoded
`semiauto` on the Auto chip, and the chip's own label follows the build: the
route rewrites it to `Semi-auto` whenever `isSemiAutoBuild` says so, which is
also what the Main tab's verdict sentence and the summary's Run row pill read.

The relay is the one reason that is not in the ten characters. `isSemiAuto` in
`codec.ts` answers for the combi's own three flags and knows nothing else;
`isSemiAutoBuild` in `full-code.ts` adds the loadout's relay, and it is the one
question whose answer needs both halves. `encode` and `decode` take a
`forcedSemiAuto` flag for it — the word "relay" never reaches the codec, so the
caller that knows the reason is also the one that names it in a warning.

That is a page decision, not a format one. Do not remove `semiauto` from
`codec.ts` to match the picker: it is slot 2's `H`, and dropping it would make
every semi-auto code ever written unreadable.

## Which characters a code may use

The separators are chosen for word-wise selection (double-click, Option+Shift+Arrow), which stops at `-` but not at `_` or `.`. So `-` appears exactly once, between the loadout and the combi, and the combi half is `[0-9A-Z]` only — `0` is its one "off" character (manual mode, Any goal, any episode, no boosts, no random boost, none of a power group, any floor, no action) — so the ten characters the game takes select on their own. Inside the loadout, `.` separates treasure slots, `_` joins a slot's alternatives, and `__` is Any; none of them breaks a word, so the loadout selects whole. Do not put `-` anywhere but the section split, and do not bring a word-breaking character into either half.

## Hard errors vs soft warnings

`decode` throws only when a code is unreadable: wrong length, unknown version, an unknown character in a slot, or a tower floor that is not three digits up to `100` (or slots 8-9 not `00` there). It returns `{ combi, warnings }` and never throws when slot 2 (`A` vs `H`) disagrees with the flag slots, when an auto run says Score or a manual one Any, or when a code carries what its episode or mode has no room for, because hand-typed codes can contradict themselves. `isSemiAuto` is always the authority; `encode` normalizes slot 2 to match it. Keep that split — the UI depends on being able to show a contradictory code rather than refusing it.

## The exhaustive test

`src/routes/combi-name/exhaustive.test.ts` round-trips all 21,243,552 combinations a code can carry — what an episode has no room for is not varied there — and asserts encoding yields exactly 10,621,776 distinct codes (the auto/semi-auto character is derived, so the auto family collapses, and a manual run drops its action). Both numbers are hardcoded; changing the configuration space means recomputing them, and a mismatch usually means a table changed size rather than that the test is stale. Both tests also carry an explicit 300s timeout: their runtime is the size of the format — about 50s each on a laptop since goals became a set and tripled the space — and the 5s Bun allows by default was already tight on a CI runner at a sixth of it.

It covers the combi section only. A loadout's alternative treasure slots make its space open-ended rather than a fixed count to enumerate, so the loadout is instead covered by a seeded round-trip sample in `full-code.test.ts` — encode 2,000 random loadouts, decode each back, and check the result re-encodes to the same code.

## The loadout section

`src/routes/combi-name/loadout.ts` owns the loadout grammar — `encodeLoadout`, `decodeLoadout`, the fixed `C R P T` group order, and its own `LOADOUT_VERSION` character, independent of the codec's `VERSION` above. `src/routes/combi-name/catalog.ts` resolves every cookie, relay, pet, and treasure id against `assets/index.json`. That file doubles as the wire-format table: its keys are the ids a loadout carries on the wire, so a key must never be renumbered once a code could have used it. The combi section protects the equivalent promise by bumping `VERSION` whenever a table's order changes; `assets/index.json` has no version character, so the same promise is kept by where an id comes from instead: it is the entry's own number on cookierunhub.com in base 36 (a blessed treasure's is its unblessed form's plus 23,328), so nothing in this repository assigns one, and `verifyStructure`, run over the committed file by the suite, checks every id against the page its `url` names. An entry the site stops listing is kept and marked `retired`, never deleted. The ids moved once, wholesale, when the catalog's source changed from cookierundb.com to cookierunhub.com — the owner chose that break over carrying a translation table, and `LOADOUT_VERSION` stayed `1`. `src/routes/combi-name/full-code.ts` joins the two sections into `loadout-combi`, or just the bare combi when there is no loadout; `src/routes/combi-name/index.ts` encodes and decodes through `full-code.ts` exclusively, never calling `encodeLoadout`/`decodeLoadout` or `encode`/`decode` itself.

Encoding a loadout always writes its canonical form: ids sorted within a slot, whole slots sorted against each other whenever the order flag is `U` (order doesn't matter), and a single slot always written `U` since there is nothing to order. `decodeLoadout` does not have the codec's hard/soft split above — there is no warning path — but it is just as forgiving of a non-canonical code in its own way: it decodes one exactly as written rather than rejecting it, and only re-encoding snaps it back to canonical form.

Each treasure id may be followed by a level: nothing for +0, one digit for one level, two for a run `min` then `max`. `Loadout.treasures` holds `TreasurePick { id, levels }` for it, built with `treasurePick`, where `levels` is a set — any levels at all, never none. A set that is not one run goes on the wire as one copy of the id per run (`levelRuns` finds them), lowest first, so `0FZ02_0FZ59` is 0FZ at +0-2 or +5-9. Decoding merges every copy of an id in a slot back into one pick, overlapping or not; encoding rejects a slot that lists an id twice, since a `Loadout` holds each treasure once per slot. Canonical form writes maximal runs, +0 as nothing and a one-level run as one digit; within a slot picks still sort by id alone, while unordered slots sort by their whole written string, levels included. No digits reading as +0 is what keeps every earlier code meaning what it did, which is why `LOADOUT_VERSION` stayed `1`. On the page, `<entry-tiles>`'s `levels` property carries the sets beside `selected`, and `writeLoadout` writes options, then picks, then levels, since each write prunes against the one before.

## Scope

The combi section still does not model the cookie, relay, pet, or treasure: the game already stores those four in the combi, which is precisely why the 10 characters are spent on everything else. Don't add them to `codec.ts`. The loadout section is the exception — it exists to model exactly those four, for a code that needs to carry them anyway.

Route-only logic stays in the route. The codec is imported by exactly one page, so it lives at `src/routes/combi-name/codec.ts` rather than in `src/lib/`; the same is true of `loadout.ts`, `catalog.ts`, `full-code.ts`, `hints.ts`, `art.ts`, `state.ts`, and `summary.ts`.

## One code, one state

The page holds exactly one thing: a `FullCode`. Every control writes it and the code bar writes it, and everything on screen is rendered from it by the route's single `render`. There is no second copy of the code and no separate reader — building a code and reading one are the same screen, which is why `<code-bar>` is both the output and the input. The bar draws only the combi section (`showAfter` the separator) and the ⋯ menu's Copy code copies only that, since those ten characters are what the game takes. The menu's Show full code (`#code-full`, `aria-pressed`) swaps the bar and Copy code to the whole code and back, remembered under `combi-name:full-code` (`storedFullCode` / `rememberFullCode` in `state.ts`); the whole code stays the page's state, its link, its saves and the editor's text. The page does draw a summary of the build (`<build-summary>`, see the `ui-components` skill), but it is not a second rendering for `render` to keep in step with the first: `summaryOf` in `src/routes/combi-name/summary.ts` builds the summary's rows from the same decoded `FullCode`, in the same `render` pass that writes every control, so the summary cannot say something the code and the controls disagree with.

A treasure slot's `legend` is one of those values: `render` writes it from `full.loadout.ordered`, the order flag the decoded code actually carries, not from the `treasureOrder` chip group beside the heading. The two can disagree — with fewer than two slots filled there is nothing to order, so canonical encoding always writes a single slot `U` regardless of what the switch asked for (see "The loadout section" below) — so the labels read `Slot 1` / `Slot 2` / `Slot 3` only once the code itself carries an order, and `Any slot` otherwise, even while the switch still reads "Exact order". The labels follow the code on purpose: the switch says what was asked for, the code says what got written, and a label is a claim about the code.

The treasure slots are the one place where what the page offers and what the format allows come apart. `optionsFor("treasures")` leaves out retired entries and any family named in `HIDDEN_TREASURE_FAMILIES` (empty today — see the `assets` skill) — but a code can still carry one, so `writeLoadout` appends any carried id the offered list lacks to that slot's own `options`, and writes the options before the picks. Both halves matter: a slot prunes a pick its options do not hold, and the two are separate writes. Without it, opening a saved link would quietly drop a treasure and rewrite the code in the address bar.

A treasure slot's options carry a fourth field, the entry's kind — `base`, `evolved` or `blessed` — which `catalog.ts`'s `kindFor` reads off the index's `N`/`E`/`B` and the picker draws as a badge, a coloured ring and a filter row. It is display only: no slot of the wire format holds it, and a code says which treasure, never which form of it, because the id already does. The route writes it in two places, `pickerOptions` for the offered list and `treasureOptions` for a carried id the picker hides, the same pair `labelFor` and `imageFor` are written in. The three `<entry-grid>` pickers — cookie, relay, pet — take the plain triple through `tileOptions`: nothing a cookie or pet picker holds evolves. `tileOptions` also puts Any at the head of each of those three lists, under the tile's own None — `catalog.ts`'s `anyIdFor` is `_` repeated to the section's width, and `labelFor` names it "Any cookie" or "Any pet", so `describe.ts` and the tooltips read it without learning the sentinel. It is a value the wire format carries, not a display state: `encodeLoadout` and `decodeLoadout` skip `checkId` for it in the `C`, `R` and `P` groups only, and `isEmptyLoadout` counts a slot holding it as filled. `_` is outside the `[0-9A-Z]` alphabet every id in `scripts/utils/asset-ids.ts` is written in, so no guard is needed at that end and no growth of the catalog can collide with it. `LOADOUT_VERSION` stays `1` because the change is additive — every code written before it decodes to exactly what it did.

A code typed into the bar is decoded on every keystroke. A code that does not read yet is not an error to argue with: the controls are left exactly where they are, and the bar says how many of the ten characters have arrived. Only a code that decodes is applied. That distinction is the reason `readDraft` tests the length before it calls `decodeFull`, rather than letting the codec's own error speak for a half-typed code.

## Where the code lives between visits

`src/routes/combi-name/state.ts` holds it in two places, and neither is trusted on the way back in: the address bar, so a build is a link someone can send, and `localStorage`, so closing the tab does not throw the last build away. A link wins over the remembered code — someone who followed one asked for that code, and their own build is one Reset away. The page writes the hash with `history.replaceState`, since one history entry per keystroke would bury the page they arrived from, and every storage call is wrapped the way `theme-toggle`'s are. A code that arrives from either place is decoded through `decodeFull` inside a `try`; both outlive the page that wrote them, and a hash can be typed by hand.

`src/routes/combi-name/saved.ts` is a third place, and the only one someone fills on purpose: a list of `{ code, description, stats?, savedAt }` — the description may run several lines, kept as typed apart from blank edges; `stats` (`stats.ts`) is Score, Money, Exp and Boxes as `{ min, max }` ranges and Time as seconds, left off when empty, and a malformed field read back is dropped rather than the entry — under its own `localStorage` key, newest first, one entry per code — saving a code again replaces its description and moves it to the top. The code is the entry's identity, so there is no separate id: `updateSaved` rewrites an entry's code and description where it stands, and refuses (`reason: "taken"`) to move it onto a code another entry holds rather than merge two notes. Read back the same way as the other two: an entry not in that shape is dropped, and Load and Edit decode through `decodeFull` inside a `try`, so a saved code a later format can no longer read says so instead of breaking the page. The list is light DOM drawn by the route itself, outside `#build`, so its description box is not a form control `#build`'s own `input` listener hears.

The drawer's `#saved-tools` (hidden under two entries, which also clears the filter so a hidden filter cannot hide the last row) holds a search, three facet selects and Sort by. Filtering is `filterSaved`: every search word must appear in the note, the code or the row's run chips; the mode, goal and episode facets (`RUN_FACETS`, `runFacets`) are `describeRun`'s first three chips, so a filter offers exactly what rows say, and `facetValues` lists only values the list holds. A code that no longer reads has no run, so any facet drops it. `#saved-nomatch` shows when a non-empty list filters to nothing; the filter is not remembered. Sort by (`#saved-sort`, options from `SAVED_SORTS`) is a view only too: `showSaved` draws `sortSaved(filterSaved(entries, filter), sort)` while `savedEntries`, storage and export keep the stored newest-first order. Newest is that order, Oldest its reverse, and Score/Money/Exp/Boxes/Time put the most first by a range's top then its floor, entries without the stat last, ties in stored order. The pick is remembered under `combi-name:saved-sort` (`storedSort` / `rememberSort`). Anything that needs a row's place on screen — Delete's focus hand-off — reads it from the DOM, not from `savedEntries`.

Each row shows Load and a `<details class="more">` menu holding Copy link, Share (when `canShare`) and Delete, so a row is two buttons rather than five. There is no separate Edit: Load always opens the entry, since Load and Edit differed only in whether a later save wrote back, and the save box already asks that (Update or Save as new). The route closes the menu on a pick, on Escape (focus back to its summary), on a click elsewhere, and when another opens; `toggle` does not bubble, so the document hears it in the capture phase. The same wiring covers the code panel's `#code-menu` (Edit code, Copy code, Copy link, Show full code, plus Cancel while an entry is open, in that order — Reset sits in the panel's row instead, beside Save), since `closeMenus` reaches every `details.more[open]` on the page. The list sits in `#saved-drawer`, a modal `<dialog>` the top bar's Saved button opens (its `#saved-count` follows `savedEntries.length` in `showSaved`). Copy link, Share, Delete and a refused store report in the page's one banner, which is inside the drawer while it is open (see "Where messages go" below). A successful Load closes the drawer first and then says "Loaded X." — unless the code read with changes, whose warning says more; a Load that no longer decodes keeps the drawer open and says so in the banner there. Deleting an entry moves focus to the next row's Load, as the menu items are hidden while it is shut, or to the drawer's Close button once the list is empty.

Delete all (`#delete-saved`, last in the drawer, under Import and export, in `#delete-all` which `showSaved` hides while the list is empty) is the one click that cannot be undone, so it asks on the page rather than through `confirm()`, which a browser can switch off: `#delete-confirm` names the count and suggests exporting first, and takes the button's place (`askDelete` swaps the two, since the question has its own Delete all), and focus lands on Keep them (`#delete-cancel`, focus back to Delete all) rather than on `#delete-yes`. Confirming runs `clearSaved`, closes the open entry if there is one, says "Deleted all N saved codes." and moves focus to Close. `showSaved` and the drawer's `close` both put the question away, since its count could go stale.

The save form (`#save-form`, the note at the top of the content, labelled by `#note-label`) has two jobs, switched by the route's `editing` variable (the code of the entry open, or null). Load opens an entry, closes the drawer and fills the box with its note and the four `#stat-*` boxes under it with its stats; Save opens one too — the entry it just added, on its code, note and stats as typed, rather than emptying the boxes — and Save as new (`#save-new`) does the same, moving off the entry that was open. It is not called New: it does not start a blank code, it saves the one on screen as an entry of its own. Submit — the code panel's `#save` button, which reaches the form through `form="save-form"` and reads Save or Update — is then Update, which writes the code panel's code and the box's note into that entry and leaves it open on its new code, note and stats as typed, while Cancel, Escape, Reset and deleting the entry all close it, and loading another entry moves it there. `markCurrent`, which `render` calls, keeps the form in step: the code panel's visible heading `#code-heading` reads "Editing saved code" rather than "New code" (with `data-editing`, which draws it and the panel edge in a dashed accent), Save reads Update, Cancel shows, and Save as new — a button of its own in the code bar's row beside Save, not in the menu, which hands focus to Save once it hides behind its own click — shows only while the code on screen is one no entry holds — the list keeps each code once, so saving a saved code as new would overwrite that entry. There is no line under the box naming the entry: "Loaded X." in the banner already does, and a second message beside it was one too many.

The code panel's Copy link builds the same link from what is on screen — the code, and the note and stats in the save boxes — so a build can be sent before it is saved; a stat box that does not read stops it the way it stops Save. An entry leaves the browser two ways. Copy link builds a link whose hash is `#CODE?note=…`, the note as base64url of its UTF-8 bytes — no space, `+` or `%` for a chat app to cut the link at, and non-Latin notes shorter than their percent-escapes; a value that is not valid base64url or UTF-8 reads as no note (`shareHashFor` / `noteInHash` in `state.ts`; `codeInHash` ignores everything from the `?`), and puts it on the clipboard. Stats ride beside it as plain `&money=12000-15000&time=245` (`statsInHash`), a value that does not read left out; Share sends the same link through `navigator.share`, and the row only offers it where `canShare` finds one, since without a sheet it would duplicate Copy link. The page's own hash never carries a note — `publish` writes the build alone — so a note in the hash on load or on `hashchange` came from a link, and `offerNote` puts it, and any stats, in the save boxes rather than saving them. A stat box that does not read stops Save or Update: every such box is marked `aria-invalid`, the first takes focus, and the banner names each one (folded under "N stats do not read" when there are several). Export and import use the text `formatSaved` writes: each code on its own line, its stats under it one per line as `money: 12000-15000`, then its note with every line quoted `>`, a blank line between entries. The quote is what separates a note from a code, so a note may contain anything. `parseSaved` also takes bare codes and shared links, canonicalises each code through `decodeFull`/`encodeFull`, reads a code listed twice once, and reports unreadable lines instead of failing. `importSaved` adds only codes not already saved, so a note someone wrote for themselves is never overwritten by an import.

## Where messages go

Every message the page shows goes to one `<notice-bar id="notice">`, inside the sticky `.codepanel` right after `<code-bar>`, and nowhere else. Inside the panel for keyboard and screen-reader order, next to the code it is mostly about, but drawn as a snackbar: `.codepanel notice-bar[type]` is `position: fixed` at the bottom centre of the window (sticky makes no containing block, so fixed escapes the panel), over the page rather than in it, so a message coming or going never moves anything at any width. The panel is pinned to the top on a wide screen only. Under 48rem it scrolls away with the page — a full code there would hold a third of the screen — the tab strip sticks to the top alone, and a floating `#to-top` button (bottom right, shown by an IntersectionObserver while the panel is out of view, never on a wide screen) scrolls back to it and focuses Save. While that button shows, the snackbar steps up above it so the two never overlap. Inside a drawer the banner sits in line under the header instead; the old `#warnings-banner`, `#save-status`, `#saved-status`, `#transfer-status` and the route's use of the code bar's `message`/`invalid` are gone. The code bar's own line under the code is left to the bar: it carries the tap hints for its runs, which label the code rather than notify. The route writes through two helpers: `sayAboutCode` for a message about the code on screen, and `say` for everything else. `render` (via `showWarnings`) shows a decode's warnings as `warn` with the title "Read with changes", and otherwise clears the banner only when it holds a message about the code — so a build change takes down a stale warning, a paste or a copy, but not "Saved X." or a refused store. A caller with something to say about the code it just applied says it after `render` returns.

| Message | Type | Helper |
| --- | --- | --- |
| Decode warnings, "Read with changes" plus the list | warn | `sayAboutCode` (from `render`) |
| Unreadable code while typing (the codec's error) | error | `sayAboutCode` |
| Typing progress ("3 of 10 characters.", "Type or paste a code.") | info, `hold` until `code-close` | `sayAboutCode` |
| "Code pasted." (only when the paste read clean) | info | `sayAboutCode` |
| Copy code / Copy link worked; clipboard blocked (Copy link with the URL) | info / error | `sayAboutCode` |
| "Saved X.", "Updated X.", "Loaded X.", "Deleted X." | info | `say` |
| Storage refused, "already saved as", "no longer reads" | error | `say` |
| "That entry is gone." | warn | `say` |
| Link-note offer, "this link's code is already saved" | info | `say` |
| A row's Copy link worked / blocked (with the URL) | info / error | `say` |
| Import added (info), added but skipped lines (warn), nothing read, refused or nothing to export (error); export copied or downloaded (info) | info / warn / error | `say` |

Cancel and Escape in the note clear a message that is not about the code (`unsay`). A drawer is a modal `<dialog>`, so the page behind it is inert: `openDrawer` moves the same element into the open drawer's `.sheet`, after its `header`, and the drawer's `close` handler — which Escape, Close and a backdrop click all pass through — puts it back after the code bar (`bringNoticeHome`). A successful Load also calls `bringNoticeHome` straight after `savedDrawer.close()`, so "Loaded X." is announced from the page rather than from the closing dialog. One banner, always the one in view.

A few rules keep a warning from being lost or misread. `openSaved` hands back the decode warnings (null when the code no longer reads), and Load says "Loaded X." only when there were none — the same test the paste path uses — so a stale warning about something else (an import's skipped line, "That entry is gone.") is replaced rather than swallowing the line. `offerNote` takes the warnings a link's code was read with: with none it says its sentence as info; with some it re-shows the warning with the offer as one more line, so neither hides the other. `code-close` clears an about-code error, since the bar is back to showing the built code, and otherwise releases held typing progress. The ✕ fires `notice-dismiss`; when the ✕ had focus the route moves it to the open drawer's Close, or to `#save` on the page.
